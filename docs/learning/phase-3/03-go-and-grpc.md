# Go, protobuf and gRPC

## What protobuf contributes

`proto/peerscreen/media/v1/media.proto` defines the commands and message fields exchanged by the services. A field has a type and a stable numeric tag. Generated code gives the caller a Go method such as `SubmitProcessingJob(ctx, spec)` and gives the server the corresponding interface method. Both sides use the same versioned package.

This is useful at a service boundary because a caller should not invent ad hoc JSON shapes or depend on another service's SQL tables. Protobuf does not replace validation: a string can still contain an invalid UUID, and a numeric field can still exceed policy. `ValidateSpec` checks canonical identifiers, the source key/checksum relationship, source size, supported recipe and previously consumed attempts.

The official Go plugins generate messages and gRPC client/server code. A pinned pure-Go protobuf compiler provides descriptors, so the repository does not depend on an unrecorded system `protoc` installation. `npm run proto:generate` regenerates the files. `npm run proto:check` compares generated bytes to the checked-in code and fails on drift. Add fields with new tags; do not reuse an existing tag for a new meaning.

## Read the important Go types

`Server` embeds the generated unimplemented server and holds a media `Store`. Each RPC method delegates to a short database operation. `Client` embeds the generated client and holds the underlying connection so the runtime can close it during shutdown. Embedding exposes methods from another type; it is not inheritance of database ownership.

The small `rowQuerier` interface describes `QueryRow`. Both `pgxpool.Pool` and `pgx.Tx` already satisfy it through their methods. Go does not require an `implements` declaration. This lets `readJob` operate either outside a transaction or inside one that holds the job lock.

Pointers such as `*pb.JobSnapshot` allow a caller to pass a structured value without copying its whole contents. `nil` remains a possible input and is rejected where required. Errors are returned explicitly. A domain conflict gets a gRPC status code; raw SQL errors become a bounded unavailable response rather than exposing a connection string or database statement.

## Contexts define request lifetimes

Every RPC takes `context.Context`. The client applies a five-second timeout, and the server applies its own five-second bound. A caller's shorter deadline is still honored. PostgreSQL operations receive that same context. Encoding does not keep an RPC open: the worker uses a separate thirty-minute attempt context and periodically makes short heartbeat requests.

`defer cancel()` releases timer resources. `defer tx.Rollback(ctx)` protects all early returns from leaving a transaction open; a successful commit makes the deferred rollback harmless. A heartbeat failure cancels the attempt context, terminating the current media subprocess rather than letting a disconnected worker continue indefinitely.

## Interceptors authenticate service roles

An interceptor runs around each RPC. The client adds a private bearer credential as metadata. The server uses constant-time comparison and checks the role against the requested method. Catalogue credentials allow submit/get/retry/cancel. Worker credentials allow claim/get/heartbeat/complete/fail. A worker cannot authorize itself to create a product video or submit arbitrary catalogue-owned work.

These credentials are independent of Google OAuth and PeerScreen browser sessions. They stay in ignored local configuration and scoped server environments. The worker receives no database credential or Google secret. The current transport is private and local; a public/cross-host deployment needs its separate TLS and broker-access configuration.

## Status codes are part of the contract

| Code                 | Meaning in this implementation                        |
| -------------------- | ----------------------------------------------------- |
| `InvalidArgument`    | Invalid ID, input policy, progress or descriptor      |
| `Unauthenticated`    | Missing or wrong service credential                   |
| `PermissionDenied`   | Authenticated service used a forbidden method         |
| `NotFound`           | No durable job with this ID                           |
| `AlreadyExists`      | An ID was reused with conflicting input/action        |
| `FailedPrecondition` | Stale/cancelled attempt or exhausted/ineligible retry |
| `DeadlineExceeded`   | The call's allowed time elapsed                       |
| `Unavailable`        | A dependency could not complete the command           |

The caller distinguishes retryable uncertainty from an explicit rejection. Retrying an uncertain claim uses the same claim request ID. Generating a new ID on every network retry could create a second attempt after an ambiguous result; the durable request identity closes that window.

## Goroutines and bounded work

The API runs separate submission, lifecycle and reconciliation loops. The coordinator runs scheduling/outbox maintenance beside its gRPC server. The worker processes one claimed attempt at a time and runs a heartbeat goroutine during encoding. Channels signal when those goroutines finish; shutdown cancels their context and waits for completion.

A mutex protects the worker's current progress while the encoder callback and heartbeat goroutine access it. The Go race detector checks that synchronization. The tests also cancel the running loops and require shutdown within a bound. Kafka clients using `BlockRebalanceOnPoll` close with `CloseAllowingRebalance`; ordinary `Close` can wait indefinitely if the final poll still holds the rebalance lock.
