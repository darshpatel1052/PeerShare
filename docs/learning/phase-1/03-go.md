# Learn Go by following this service

The service uses Go 1.27.2, pinned in `go.mod` as the toolchain. The host originally had 1.27.1; the patched release was verified and downloaded for this implementation. The standard HTTP router keeps the transport code visible instead of hiding it behind a large framework.

## Modules, packages and imports

`go.mod` identifies the module and dependency versions. A module can contain several packages. `go.sum` records dependency content checksums; it complements version pins by detecting unexpected downloaded content. Direct dependencies are packages our code imports; indirect dependencies support those packages.

`cmd/peerscreen` is `package main`, which contains the executable entry point. Packages under `internal` separate configuration, HTTP, authentication, SQL and limits. Names beginning with an uppercase letter are exported outside their package; lowercase names are package-private. Export a small useful API, not every implementation detail.

The four direct dependencies have concrete jobs: `pgx` speaks PostgreSQL and provides a pool; `go-redis` talks to Redis; `x/crypto/argon2` implements the password-hashing primitive; `google/uuid` generates/parses identifiers. Go's standard library handles HTTP, JSON, time, logging, randomness, hashes, cookies, contexts and signals.

## Structs and JSON tags

A struct groups fields into a typed value. In `store/models.go`, `User` groups ID, email, display name, role and creation time. A field tag such as `json:"display_name"` controls the JSON property name. A tag of `json:"-"` excludes internal data, such as a channel's owner ID or storage key, from serialization. `omitempty` omits an optional field from JSON.

This is a useful boundary: the store can carry internal keys needed by the server without exposing all of them to the browser. Password hashes are returned separately from public `User` rather than being a casually serializable user field.

`Me.Channel` is `*Channel`. A pointer can be nil, so the response can distinguish “this user has no channel” from a channel whose fields happen to be empty. It serializes as `null`, matching the OpenAPI contract.

## Functions, methods and pointers

A function takes inputs and returns outputs. A method adds a receiver: `func (s *Store) Channel(...)` means this operation belongs to a Store instance and uses its connection pool. `func (a *App) login(...)` uses the API instance's configuration, hasher and dependencies.

The `*Store` receiver is a pointer. It refers to the existing object rather than copying the pool-containing struct for each call. A pointer does not automatically make concurrent mutation safe. Here the pool is designed for concurrent use; request-local values remain local, and shared mutable test buffers use a mutex.

Slices such as `[]Video` are variable-length sequences. We initialize an empty page with `make([]Video, 0, limit)` so JSON produces `[]`, not `null`, and allocates sensible initial capacity. A slice's length is how many elements it currently contains; its capacity is available backing-array space. Appending may reuse that array or allocate another one.

Maps associate keys with values. HTTP tests use a map of header names to values; the router registers a map of allowed methods for fallback responses. Avoid assuming map iteration has a stable order. We do not use a map as an authoritative session store because process restarts and multiple API instances would lose or disagree about sessions.

## Interfaces and structural typing

An interface describes behaviour through methods. `http.Handler` has `ServeHTTP(ResponseWriter, *Request)`. The router is a handler, and middleware returns another handler wrapping it. `http.HandlerFunc` adapts an ordinary function to that interface.

The store defines a small `queryRower` interface with `QueryRow`. Both `pgxpool.Pool` and `pgx.Tx` have that method, so both satisfy it without an explicit `implements` keyword. `saveSession` can therefore insert through a pool or inside an existing transaction. This interface exists because two real implementations need the same operation; we do not introduce an interface for every struct just to create layers.

The `Scan(...any) error` interface is used for row scanning because both a single row and a row iterator can supply the same scan operation. SQL fields must match scan destination order and type; integration tests exercise that real mapping.

## Multiple return values and errors

Go commonly returns `(value, error)`. `if err != nil` makes the failure path explicit. Callers must avoid using the returned value as if the operation succeeded. Early returns keep the successful path readable.

Sentinel errors such as `store.ErrNotOwner` describe application outcomes. The HTTP layer maps them to a readable status/code. `errors.Is` checks whether an error represents that outcome, including through wrapping. `errors.As` extracts a PostgreSQL error type so we can recognize a unique-constraint violation and its constraint name.

We do not send raw SQL errors, connection strings or passwords to a browser. Unknown dependency errors become a controlled 503. The request ID connects the readable response to structured server logs. This limits disclosure but also means richer internal diagnostics will need deliberate redaction when observability expands.

An expected failure is an error, not a panic. Panics represent broken assumptions or unexpected faults. The request wrapper recovers a panic into a generic 500 and logs a request ID without logging the panic value, which could contain sensitive data. A recovery wrapper cannot undo a database transaction that was already committed; transactions and safe state changes still matter.

## Defer and resource lifetime

`defer` schedules cleanup when the surrounding function returns. After beginning a transaction, the code defers rollback. Any failed query or authorization check can return early and still attempt cleanup. A successful commit ends the transaction; the deferred rollback then has nothing left to roll back.

Other examples are closing a pool/client at process exit, closing query rows, releasing a password-work slot, cancelling a timeout context and closing an HTTP response body. Defer runs at function exit, not after the next block, so placing many deferred resources inside a long-running loop can delay release unnecessarily.

## Context: deadlines and cancellation

`context.Context` carries a deadline, cancellation and carefully scoped request values. The HTTP wrapper creates an eight-second operation context. Store and Redis calls receive it, so abandoned work can be cancelled. The database also has its own statement timeout; these are complementary boundaries.

The context contains a server-generated request ID. Authentication adds a typed `User` under a private key type. A private key type avoids accidental collisions with other packages' keys. This request context is not durable state: sessions and ownership still live in PostgreSQL.

Context cancellation cannot interrupt every CPU instruction. Argon2id finishes the calculation it has already started; the helper checks cancellation before publishing a result and honours cancellation while waiting for a slot. We bound concurrent calculations separately.

## Goroutines, channels and bounded concurrency

A goroutine is an independently scheduled execution path started with `go`. `net/http` already handles requests concurrently; manually starting another goroutine for each query would usually make lifetime management harder.

The process starts one goroutine for `ListenAndServe`, because the main path must also observe shutdown signals. A buffered error channel lets that goroutine report listener termination. A `select` waits for either a listener error or a shutdown signal.

The password hasher uses a buffered `chan struct{}` as a semaphore. Sending an empty value acquires one of two slots; receiving it in deferred cleanup releases the slot. When both slots are occupied, another request waits or exits on context cancellation. Each current hash uses 64 MiB of Argon2 memory, so an unbounded number of simultaneous login requests would be costly even with valid code.

Integration tests also start concurrent channel-creation and limiter requests. A WaitGroup waits for those goroutines to finish, and atomic/mutex-protected values collect results without data races. `go test -race` instruments accesses to detect unsynchronized shared-memory behaviour. A race-free test run does not prove all possible concurrency interleavings or the absence of database-level races; PostgreSQL constraints and transaction tests address those separately.

## Graceful shutdown

`signal.NotifyContext` turns SIGINT/SIGTERM into cancellation. The main function calls `http.Server.Shutdown` with a ten-second budget, stops accepting new connections, and allows active requests to finish. A forced close is a fallback if that budget expires. The server's request/body/header timeouts also bound normal operation.

This is HTTP process shutdown, not worker-job durability. Future encoding workers will need persisted leases, heartbeats and fenced completion; killing a process is not proof of safe job recovery.

## Commands and testing

The same executable supports `serve`, `migrate`, `seed-fixture` and `healthcheck`, with explicit responsibilities. Migrations and fixture import happen before serving the demo. Embedded SQL means the compiled program carries the migration source rather than depending on the caller's current directory.

Use `npm run api:vet` for Go's static checks, `npm run api:test` for unit/race checks, and `npm run test:integration` for a real isolated PostgreSQL/Redis run. Integration cases deliberately skip in the unit-only command; the integration runner explicitly detects unexpected skips.

The Node wrapper finds the Go executable, pins the toolchain and uses ignored local caches. On this Linux machine it can call the Snap compiler directly because Snap's wrapper could not run inside the restricted shell. That is an environment workaround, not a Go application architecture requirement.

## Exercises

Follow `POST /api/v1/channels` through the handler, `identity(r)`, store method, SQL and JSON response. Identify which values are request-local, which objects are shared safely and which state is durable. Explain what changes if the context times out before versus after a transaction commit. Find every defer that protects a resource on an early return.
